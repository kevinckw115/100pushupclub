# Account deletion operations

Run `node scripts/deletion-worker.mjs` from tools/backend in a server environment with DELETION_DATABASE_URL (privileged database connection), DELETION_API_URL, DELETION_ADMIN_KEY and optional DELETION_MAX_STEPS (default25, maximum100). Never use these secrets in a client build. The worker prints counts only. Configure a supervised schedule at least every minute, alert on failed/aged jobs and verify the seven-day completion target before beta. No hosted schedule is provisioned here.

Each data step is transactional and bounded. A failure retains the phase and a sanitized CLEANUP_RETRY code with a one-minute pause. Ownership candidate changes cause a retry after ordered locking. Auth deletion uses the server Admin API only after private data cleanup; completion requires verified Auth-row absence. Repeating a completed job has no effect. Staff should inspect job status/age/error code through a privileged operations connection, never request a user's full database or status proof. Existing moderation audits remain append-only; configure and disclose justified retention before release. Verify backup expiry and restore handling so restored deleted accounts remain unavailable until deletion jobs are reapplied.

The verified web deletion surface and policy/support URLs must be deployed to owner-controlled HTTPS hosting after review. Configure Auth email delivery and publishable project settings there; no deletion may be triggered by an email address alone. Retain status proofs only on the requesting device, never telemetry, URL query strings or service logs.

The standalone staging website in apps/site serves `/delete-account/`, `/policies/` and `/support/` without exposing the full mobile web app. It does not use browser SQLite or require COOP/COEP. Deletion works without an installed app or prior local sign-in: it requests an existing-account-only OTP (create_user=false), verifies ownership and requires explicit confirmation. A suspended account can use this path without ordinary profile bootstrap. Set SITE_SUPPORT_EMAIL only after mailbox delivery is verified; the mobile app separately uses EXPO_PUBLIC_SUPPORT_EMAIL. Preserve TLS, restrictive ingress limits and Auth email settings. See docs/15-website-operations.md. No hosted website is claimed.

The prepared Supabase Cron schedule invokes the staging-operations Edge Function, which reuses the worker and metrics, authenticates a dedicated scheduler secret, serializes runs using a session advisory lock and optionally signals a heartbeat monitor. See docs/16-hosted-operations.md for browser-only setup, secrets and remaining gates. No hosted schedule is provisioned by committing these files.
